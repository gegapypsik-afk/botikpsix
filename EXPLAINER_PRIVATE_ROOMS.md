# Приватные голосовые комнаты (join-to-create) — пояснительная записка

## Background

### Для тех, кто не знаком с ботом (можно пропустить, если вы в теме)

Этот проект — Discord-бот на `discord.py`, который живёт в одном большом файле
`bot.py`. Исторически он вырос вокруг **системы тикетов**, а со временем оброс
модерацией, автомодом и ИИ-собеседником. Несколько архитектурных решений повторяются
из модуля в модуль, и новый функционал важно встроить в те же рельсы:

1. **Единое хранилище настроек.** Класс `Storage` держит всё состояние в `data.json`
   (по гильдии, то есть по серверу). Функция `_default_guild()` описывает форму этого
   состояния, а `Storage.guild()` делает «мягкую миграцию»: если у старого сервера в
   файле не хватает какого-то ключа, он аккуратно досыпается из значений по умолчанию.
   Это позволяет катить новые фичи без потери данных пользователей.

2. **Persistent Views.** Кнопки Discord живут внутри «View». Обычная View умирает
   после перезапуска процесса — её кнопки перестают отвечать. Чтобы кнопки работали
   вечно, discord.py предлагает **persistent views**: у View должен быть
   `timeout=None`, а у каждого компонента — стабильный `custom_id`. Такие View один раз
   регистрируются в `setup_hook` через `bot.add_view(...)`, и после этого Discord знает,
   какой код звать при клике по кнопке в старом сообщении.

3. **Фирменное оформление.** Хелпер `brand(embed, guild)` и палитра `Colors`
   обеспечивают единый визуальный стиль всех эмбедов.

> [!NOTE]
> **Гильдия (guild)** — это внутреннее название Discord-сервера в API. В коде вы
> увидите `guild` там, где пользователь сказал бы «сервер».

### Узкий контекст этой задачи

Пользователь попросил повторить популярную механику **«приватных комнат»**
(она же *join-to-create* / *temporary voice channels*): человек заходит в специальный
голосовой канал-«создатель», и бот тут же делает ему **личную** голосовую комнату,
назначает владельцем и перемещает внутрь. Управление комнатой — через панель с
кнопками (задать лимит, закрыть, переименовать, скрыть, выгнать, передать владение
и т.п.), ровно как на скриншоте из ТЗ.

До этой правки бот вообще не слушал голосовые события — не было обработчика
`on_voice_state_update`, а `intents.voice_states` явно не включался (хотя и входит в
`Intents.default()`).

## Intuition

Ядро идеи — **две реакции на одно голосовое событие** и **одна общая панель**.

Представьте себе швейцара у входа в отель:

- Гость заходит в дверь с табличкой «Создать комнату» (это `creator_channel`).
  Швейцар не пускает его толпиться в дверях, а выдаёт ключ от свежего номера и
  провожает туда. В коде: *если человек вошёл в канал-создатель — создаём новый
  голосовой канал, записываем его владельцем и телепортируем его туда.*

- Когда из номера выходит последний гость, горничная убирает номер. В коде: *если
  из отслеживаемой комнаты кто-то вышел и она опустела — удаляем канал.*

Теперь про панель. Легко представить, что панель должна висеть в каждой комнате.
Но на скриншоте есть отдельный текстовый канал `настройка-комнат` с **одной**
панелью. Значит, панель общая, а кнопки должны понимать, **чью именно** комнату
настраивать. Решение простое: когда вы жмёте кнопку, бот смотрит в хранилище — «а
какой комнатой владеет вот этот человек?» — и действует над ней.

Небольшой пример на игрушечных данных. В `data.json` для сервера появляется:

```json
"private_rooms": {
  "enabled": true,
  "creator_channel_id": 999,
  "category_id": 700,
  "interface_channel_id": 800,
  "default_limit": 0,
  "name_template": "Комната {user}",
  "active_rooms": {
    "10001": {"owner_id": 1, "locked": false, "hidden": false, "speak_restricted": false}
  }
}
```

Здесь `active_rooms` — это «журнал уборщицы»: карта «id голосового канала → кто
владелец и в каком он состоянии». Владельца ищем обратным просмотром этой карты.

> [!IMPORTANT]
> Разделение ролей у прав доступа — ключевой трюк. «Замок» и «скрытие» мы вешаем на
> роль `@everyone`, а владельцу выдаём **персональный** `overwrite` с `connect=True`,
> `view_channel=True`. Персональное разрешение сильнее общего запрета, поэтому
> владелец всегда попадёт в свою комнату, даже когда она закрыта для всех остальных.

## Code

Все изменения — в `bot.py` (плюс документация в `README.md`). Разберём по слоям.

### 1. Форма состояния и миграция

Добавлена секция по умолчанию и вписана в `_default_guild()`:

```python
DEFAULT_PRIVATE_ROOMS = {
    "enabled": True,
    "creator_channel_id": None,    # голосовой канал «Создать комнату»
    "category_id": None,           # категория, куда создаются комнаты
    "interface_channel_id": None,  # текстовый канал с панелью управления
    "default_limit": 0,            # 0 = без лимита
    "name_template": "Комната {user}",
    "active_rooms": {},            # {channel_id: {owner_id, locked, hidden, ...}}
}
```

В `Storage.guild()` — та же «мягкая миграция», что и у остальных секций, чтобы у
существующих серверов ключ появился без потери данных:

```python
if not isinstance(g.get("private_rooms"), dict):
    g["private_rooms"] = copy.deepcopy(base["private_rooms"])
else:
    for k, v in base["private_rooms"].items():
        g["private_rooms"].setdefault(k, copy.deepcopy(v) if isinstance(v, (dict, list)) else v)
```

### 2. Чистые хелперы (без Discord-магии)

- `pr_room_name(template, member)` — имя комнаты по шаблону, безопасно к кривым
  шаблонам (падение `.format()` откатывается к дефолту).
- `find_owned_room(guild, gdata, user_id)` — находит комнату владельца **и попутно
  вычищает «протухшие» записи** о каналах, которых уже нет. Это самолечение состояния.
- `create_private_room(member, gdata)` — создаёт голосовой канал с правильными
  `overwrites`, записывает его в `active_rooms`, перемещает владельца внутрь.
- `delete_private_room(channel, gdata)` — убирает запись и удаляет канал.

```python
async def create_private_room(member, gdata):
    guild = member.guild
    pr = gdata["private_rooms"]
    category = guild.get_channel(pr.get("category_id")) ...
    overwrites = {
        member:   discord.PermissionOverwrite(view_channel=True, connect=True, speak=True,
                                              manage_channels=True, move_members=True),
        guild.me: discord.PermissionOverwrite(view_channel=True, connect=True, speak=True,
                                              manage_channels=True, move_members=True),
    }
    channel = await guild.create_voice_channel(name=pr_room_name(...), category=category,
                                               user_limit=int(pr.get("default_limit") or 0),
                                               overwrites=overwrites, reason=...)
    pr.setdefault("active_rooms", {})[str(channel.id)] = {"owner_id": member.id, ...}
    storage.save()
    await member.move_to(channel, reason=...)
    return channel
```

### 3. Событие `on_voice_state_update`

Сердце механики. Две независимые проверки: «вошёл в создатель?» и «вышел, оставив
пустую комнату?».

```python
@bot.event
async def on_voice_state_update(member, before, after):
    pr = storage.guild(member.guild.id)["private_rooms"]
    if not pr.get("enabled"):
        return
    # 1) join-to-create
    if after.channel and after.channel.id == pr.get("creator_channel_id"):
        existing, _ = find_owned_room(member.guild, gdata, member.id)
        if existing:
            await member.move_to(existing)      # уже есть комната → просто вернуть
        else:
            await create_private_room(member, gdata)
    # 2) опустевшая комната → удалить
    if before.channel and str(before.channel.id) in pr.get("active_rooms", {}):
        if not before.channel.members:
            await delete_private_room(before.channel, gdata)
```

> [!WARNING]
> Обработчик голоса **не должен падать** — иначе посыпятся все остальные голосовые
> события. Поэтому создание комнаты обёрнуто в `try/except` (отдельно ловим
> `discord.Forbidden` — нет прав — и общий `Exception` только логируем).

Также в `on_ready` добавлена стартовая уборка: пока бот лежал, участники могли выйти;
пустые/исчезнувшие комнаты подчищаются, чтобы `active_rooms` не копил мусор.

### 4. Панель управления (persistent view)

`PrivateRoomInterfaceView(timeout=None)` — восемь кнопок (по `custom_id` каждая) плюс
селект «Выбрать активность». Ключевой приём — общий метод `_resolve(interaction)`:

```python
async def _resolve(self, interaction):
    gdata, channel, info = _room_owner_channel(interaction)   # чья комната?
    if channel is None:
        await interaction.response.send_message("❌ У вас нет активной комнаты...", ephemeral=True)
        return None
    return gdata, channel, info
```

Каждая кнопка сначала зовёт `_resolve`, а потом делает своё дело над найденным
каналом. Переключатели (`🔒`, `👁️`, `🎤`) правят `overwrite` для `@everyone` и
запоминают состояние в `info`. Действия над участником (`👑`, `👢`, `🔐`)
открывают эфемерное окно с `discord.ui.UserSelect`, чтобы выбрать человека.

Модальные окна `RoomLimitModal` и `RoomRenameModal` меняют `user_limit` и `name`
через `channel.edit(...)`. View регистрируется один раз в `setup_hook`:

```python
self.add_view(PrivateRoomInterfaceView())
```

### 5. Команды настройки

Главная — `!приватки_настройка`: одним нажатием создаёт категорию, канал-создатель,
текстовый канал-интерфейс и публикует панель. Плюс ручные команды на случай, когда
хочется использовать уже существующие каналы: `!приватки_создатель`,
`!приватки_категория`, `!приватки_интерфейс`, `!приватки_лимит`, `!приватки_имя`,
`!приватки_панель`, и `!приватки [вкл|выкл]` для статуса/переключения.

## Verification

Так как поднять живой Discord-шлюз в песочнице нельзя, проверка сделана на трёх
уровнях.

1. **Компиляция и импорт.** `python -m py_compile bot.py` + импорт модуля с фиктивным
   токеном. Проверено, что panel-view — валидный persistent view
   (`is_persistent() == True`), что у него ровно 9 компонентов с уникальными
   `custom_id`, и что все новые команды зарегистрированы у бота.

2. **Юнит-логика на моках.** Мок-объекты `FakeGuild` / `FakeChannel` / mock member
   имитируют Discord API. Проверены:
   - `create_private_room` — канал создаётся, владелец перемещён, запись добавлена;
   - `find_owned_room` — находит владельца, чистит протухшие записи;
   - переключатели `lock/hide/speak` — правят нужные поля `PermissionOverwrite` и
     сохраняют состояние;
   - модалки лимита (в т.ч. отказ на не-число) и переименования;
   - `transfer` (смена владельца + перевыдача прав), `kick` (в т.ч. запрет «кикнуть
     себя»), `access` (выдача/отзыв доступа);
   - `delete_private_room` — запись убрана, канал удалён;
   - `_resolve` без комнаты — эфемерная ошибка.

3. **Сценарий события.** Отдельный прогон `on_voice_state_update`: вход в создатель
   создаёт комнату и перемещает; повторный вход **не** плодит дубликат, а возвращает в
   существующую; выход, опустошающий комнату, её удаляет; при `enabled=False` бот
   ничего не делает.

Все проверки прошли (✅).

### Как проверить руками на сервере

1. Пригласите бота с правами **Управление каналами**, **Перемещать участников**,
   **Создавать приглашения**; роль бота — выше создаваемых каналов.
2. Выполните `!приватки_настройка`. Появятся категория, канал `➕ Создать комнату`,
   канал `настройка-комнат` с панелью.
3. Зайдите в `➕ Создать комнату` — вас перекинет в свежую личную комнату.
4. В `настройка-комнат` нажимайте кнопки: смените лимит, закройте комнату (проверьте
   вторым аккаунтом, что войти нельзя), скройте, переименуйте, выгоните, передайте
   владение, ограничьте право говорить.
5. Выйдите из комнаты — она должна удалиться, когда опустеет.

## Alternatives

### A. Панель в текст-чате каждой комнаты вместо общего канала-интерфейса

| Плюсы | Минусы |
|---|---|
| Кнопка всегда рядом с комнатой; не нужно искать «чью» комнату — она равна каналу сообщения | Не совпадает со скриншотом ТЗ (там отдельный `настройка-комнат`) |
| Проще определить целевую комнату (`interaction.channel`) | Панель создаётся заново на каждую комнату (больше сообщений, сложнее persistence) |
| Изоляция: посторонний не видит чужую панель | Text-in-voice можно отключить на сервере — панель тогда негде разместить |

### B. Хранить владение только в памяти (без записи в `data.json`)

| Плюсы | Минусы |
|---|---|
| Меньше кода, нет миграции состояния | После рестарта бот забывает владельцев — кнопки «ничьих» комнат мертвы |
| Не нужно чистить протухшие записи | Теряется идемпотентность (дубликаты комнат у одного владельца) |
| Чуть быстрее (нет записи на диск) | Стартовая уборка невозможна — копится мусор из «осиротевших» каналов |

Выбранный вариант (общий канал-интерфейс + состояние в `data.json`) точно повторяет
скриншот и переживает перезапуски — что важно для хостинга Railway, где передеплой
случается часто.

## Quiz

<details>
<summary>1. Почему у владельца комнаты есть персональный overwrite с connect=True, если "замок" ставит connect=False для @everyone?</summary>

**Правильно: персональные разрешения в Discord приоритетнее ролевых, поэтому владелец
входит даже в закрытую комнату.**

- ❌ «Чтобы владелец мог банить участников» — за это отвечают `move_members` и логика
  кнопок, а не `connect`.
- ✅ «Персональный `overwrite` перекрывает запрет для `@everyone`» — именно так: замок
  вешается на `@everyone`, а личное `connect=True` владельца оказывается сильнее, и он
  не запирает сам себя.
- ❌ «Иначе Discord не даст создать канал» — создать канал можно и без этого; проблема
  проявилась бы только при попытке войти в закрытую комнату.
</details>

<details>
<summary>2. Что произойдёт, если владелец снова зайдёт в канал-создатель, уже имея активную комнату?</summary>

**Правильно: бот не создаст вторую комнату, а переместит его в уже существующую.**

- ✅ `find_owned_room` вернёт существующий канал, и ветка `if existing:` просто вызовет
  `member.move_to(existing)`.
- ❌ «Создастся вторая комната» — как раз этого мы избегаем проверкой владения.
- ❌ «Ничего не произойдёт» — перемещение всё же происходит, чтобы человек не застрял в
  канале-создателе.
</details>

<details>
<summary>3. Зачем панель управления сделана persistent view (timeout=None + custom_id)?</summary>

**Правильно: чтобы кнопки работали после перезапуска процесса бота.**

- ✅ Persistent view регистрируется в `setup_hook`, и Discord знает, какой код звать по
  клику даже для старого сообщения панели.
- ❌ «Чтобы панель была видна всем» — видимость определяется правами текстового канала,
  а не типом View.
- ❌ «Чтобы ускорить отклик кнопок» — на скорость это не влияет; речь про выживание
  после рестарта (а на Railway передеплои частые).
</details>

<details>
<summary>4. Как кнопка на общей панели понимает, какую именно комнату настраивать?</summary>

**Правильно: по владельцу — ищет в active_rooms комнату, где owner_id равен id нажавшего.**

- ✅ `_room_owner_channel(interaction)` → `find_owned_room(...)` находит канал владельца.
- ❌ «По каналу, где висит панель» — панель одна на всех, и это текстовый канал, а не
  голосовая комната.
- ❌ «По тому, в каком голосовом канале сейчас человек» — необязательно; управлять можно
  и не находясь внутри, важно именно владение.
</details>

<details>
<summary>5. Почему создание комнаты в on_voice_state_update обёрнуто в try/except, а Forbidden ловится отдельно?</summary>

**Правильно: сбой обработчика голоса не должен ронять остальные голосовые события, а
Forbidden — ожидаемая ситуация (нет прав), которую логируем понятным сообщением.**

- ✅ Общий `except Exception` только пишет в лог и не даёт исключению всплыть; отдельный
  `except discord.Forbidden` даёт человекочитаемую подсказку про права бота.
- ❌ «Так требует discord.py» — API этого не требует, это осознанная защита стабильности.
- ❌ «Чтобы повторять попытку создания» — ретраев здесь нет; цель — не упасть.
</details>
